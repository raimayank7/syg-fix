Why use fake test data

A test database filled with real customers is a data leak waiting to happen.

The risk

Test and development systems are usually less protected than production: more people can reach them, copies end up on laptops, and backups are kept without care. If they hold real names, phone numbers or ID numbers, a leak there is a real leak. India's Digital Personal Data Protection Act, 2023 is about personal data of real people, so copying a customer list to test is a use that must have a legal basis, and fake data avoids the question.

What realistic means

Good test data has the shape of the real thing: names of different lengths, accented and non-Latin letters, repeated cities, dates over several years, amounts with paise, and some empty values. The generator makes names, cities with their states, dates, amounts and notes, and every number comes from a seed, so a test can be repeated.

What this generator does not make

It makes no PAN, Aadhaar, GSTIN, bank account, card or phone numbers. A made-up number can easily be somebody's real number, and a number with a valid check digit may pass as real. If you need such formats, test with the sample values that the issuer publishes in its own documentation, and never use a number that belongs to a person.

Checklist

  1. Use the generator or your own script for every test database.
  2. Use example.com addresses for e-mail so that no message can reach a real person.
  3. Do not send test e-mails or messages to the addresses of real people.
  4. Keep the seed in the test so that failures can be reproduced.
  5. Delete test data when the test ends.
Is fake data enough for performance tests?

Make as many rows as you need, up to 5,000 here, and use a script of your own for millions.

Can I use real data if I remove the names?

Not safely: other fields can identify a person. Prefer invented data.
