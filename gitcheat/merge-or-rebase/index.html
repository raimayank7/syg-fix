Merge or rebase: which to use

Both bring work from one branch into another. They leave different histories.

What each one does

  • Merge keeps both lines of history and adds a merge commit that joins them. Nothing already written is changed.
  • Rebase takes your commits and writes them again on top of the other branch. The history becomes one straight line, and your commits get new hashes.

The conflict page of this site printed the graph after a merge, a line with a branching shape and a merge commit at the top. The rebase page printed a straight line.

A simple rule

  1. Work only you have: rebase to tidy it before you share it.
  2. Work other people also use: merge, because rebasing it would rewrite commits they already have.
  3. When unsure, merge. It never hides what happened.

Conflicts

In both cases Git can stop and ask you to fix a conflict. With a merge you fix it once. With a rebase you may have to fix it for each commit that conflicts, then run git rebase --continue; to give up, run git rebase --abort.

Does rebase lose my work?

Not normally, and the old commits stay in the reflog for a while. Still, make a copy of the branch first if the work matters: git branch backup.

What does the merge commit contain?

Usually no changes of its own. It records that two lines of history were joined.
